# pixie-quest v26 验收结果数据标准

> 用途：指导验收人员执行 v26「阶段 1 + 阶段 2」验收，并以统一格式提交结果。
>
> 本文档是验收数据规范，不是验收报告。执行后请复制附录模板，填写实际结果并附原始证据。

## 1. 验收范围

### 1.1 本次必须验收

- 战斗核心纯逻辑及回归测试。
- 中毒最后一跳致死、续力条、大招后计时、答题入口守卫。
- 返回地图后的毒、冻结、续力清理。
- 最终 Boss `freeze` 技能英文事件文案。
- 精灵打码使用事件发生时的问题快照。
- 模型输出和精灵日志的安全渲染。
- 服务器配置、静态资源、模型健康检查、LLM 超时、日志落盘。
- 会话分析工具、题库审计、精灵审计。
- 题目 ID、知识点标签、动词题讲解数据。
- 地图、答题、错题本、精灵日志等基础用户流程。

### 1.2 本次不作为通过条件

以下项目属于阶段 3/4，不得因未实现而判 v26 失败：

- 错题间隔答对两次才掌握、错题复习模式、存档版本迁移。
- 无 LLM 时的完整静态教学闭环。
- 全部页面前端模块拆分。
- 移动端、键盘、焦点管理、减少动画等完整可访问性改造。
- LLM 结构化输出和小模型 A/B 优化。

## 2. 验收包目录与命名

每次验收单独建立一个目录，不得覆盖上一轮结果：

```text
v26-acceptance-YYYYMMDD-HHmmss/
├── report.md                 # 必填：人工汇总结论
├── environment.json          # 必填：环境与版本
├── results.json              # 必填：逐用例结构化结果
├── commands/                 # 必填：命令原始输出
│   ├── npm-test.log
│   ├── npm-run-check.log
│   ├── npm-run-audit.log
│   ├── npm-run-analyze.log
│   └── npm-run-audit-fairy.log
├── http/                     # 涉及 HTTP 的响应头与响应体
├── screenshots/              # 页面流程、弹窗、异常现场
├── sessions/                 # 精灵、玩家及审计 JSON
└── defects/                  # 失败用例的复现步骤和补充日志
```

要求：

- 文件名只使用 ASCII 字母、数字、`-`、`_` 和扩展名。
- 原始日志不得只保留截取后的成功片段，必须包含命令、退出码和完整错误。
- 截图不能替代数值、HTTP 状态码、JSON 或命令退出码。
- 证据路径统一使用相对验收包根目录的路径。
- 日志中的用户目录、会话 ID 等可按需脱敏，但不得改动状态、计数和错误内容。

## 3. 环境数据标准

`environment.json` 至少包含以下字段：

```json
{
  "project": "pixie-quest",
  "version": "v26",
  "commit": "填写完整 commit SHA",
  "worktreeClean": true,
  "startedAt": "ISO 8601，含时区",
  "finishedAt": "ISO 8601，含时区",
  "os": "操作系统及版本",
  "node": "node --version 的实际输出",
  "npm": "npm --version 的实际输出",
  "browser": "浏览器及版本",
  "viewport": "例如 1280x720",
  "server": {
    "host": "127.0.0.1",
    "port": 8797,
    "logDir": "实际日志目录"
  },
  "llm": {
    "available": true,
    "provider": "LM Studio",
    "model": "实际模型 ID",
    "timeoutMs": 170000
  },
  "notes": "代理、特殊启动参数或其他影响结果的条件；无则填空字符串"
}
```

若某项 LLM 用例在无模型环境下执行，必须将 `llm.available` 设为 `false`，不得用另一轮环境的结果拼接成同一次验收。

## 4. 结果状态与判定规则

每个用例只能使用以下状态：

| 状态 | 含义 |
|---|---|
| `PASS` | 已实际执行，实际结果满足全部通过条件，且证据完整 |
| `FAIL` | 已实际执行，任一通过条件不满足 |
| `BLOCKED` | 因环境或外部依赖无法执行；必须写明阻塞原因，不能视为通过 |
| `N/A` | 明确不在 v26 范围；必须引用本标准第 1.2 节或经双方确认 |

统一规则：

- “看起来正常”“基本可用”“应该没问题”均不是有效实际结果。
- 只读代码、只运行单元测试、只检查页面能打开，均不能替代对应端到端用例。
- 失败用例必须给最小复现步骤、实际值、预期值和原始错误。
- 修复后必须重新执行失败用例及其相关回归用例，并生成新的验收目录。
- 命令成功以退出码 `0` 为准；输出中的历史实验告警不得直接当作本轮功能失败，需单独说明。

## 5. 命令验收标准

将完整标准输出和标准错误保存到 `commands/`，同时在 `results.json` 记录退出码。

| 用例 ID | 命令 | 通过条件 | 必须记录的数据 |
|---|---|---|---|
| CMD-01 | `npm test` | 退出码 0；`fail=0`、`cancelled=0` | tests、pass、fail、duration |
| CMD-02 | `npm run check` | 退出码 0；无语法失败 | 检查段数 |
| CMD-03 | `npm run audit` | 退出码 0；结构、语义重复、VERB_DB、答案、拼写、跨难度错误均为 0 | 总题数、难度分布、各项汇总；刻意难度 WARN 单独列出 |
| CMD-04 | `npm run analyze` | 退出码 0；唯一题目分母等于当前题库总数；无固定旧阈值文案 | 输入日志名、题数、分析摘要 |
| CMD-05 | 自定义双日志执行分析工具 | 退出码 0；实际读取指定文件而非默认快照 | 完整命令、输入文件、唯一题目数 |
| CMD-06 | `npm run audit:fairy -- --out <验收包>/sessions/fairy-audit.json` | 退出码 0；指定文件存在且为合法 JSON；16 个事件均有结果 | 成功应答数、标签合规数、泄题数、输出路径 |
| CMD-07 | `npm start` | 服务器成功监听配置地址；启动日志无异常 | 实际地址、日志目录；端口被占用时不得拿未知旧进程结果代替 |

说明：精灵审计允许模型内容存在教学质量差异，但脚本崩溃、结果文件未生成、JSON 无法解析必须判 `FAIL`。

## 6. HTTP 与服务器验收标准

HTTP 证据至少保存：请求方法、URL、请求体摘要、响应状态码、响应 `Content-Type`、响应体。涉及写日志的用例必须使用独立临时 `LOG_DIR`，不得污染正式实验数据。

| 用例 ID | 场景 | 操作要点 | 通过条件 |
|---|---|---|---|
| SRV-01 | 静态资源 | 请求 `/`、`/nce-shared.js`、`/src/game-core.js` | 均为 200；内容类型正确；浏览器无对应 404 |
| SRV-02 | 未知路由 | 请求不存在的路径 | 返回 404，不返回页面或 500 |
| SRV-03 | 模型健康检查通过 | 启动所需模型后请求 `/llmhealth` | `ok=true`、`hasModel=true`，模型列表包含实际模型 |
| SRV-04 | 模型健康检查失败 | 使用必然不存在的模型匹配值 | `ok=false`，不得只因 LM Studio 可达而返回 true |
| SRV-05 | LLM 不可达 | 将上游指向未监听端口后 POST `/llm` | 在约定时间内返回 502 和可解析错误 JSON，不挂起 |
| SRV-06 | LLM 上游超时 | 用可控慢响应上游，并设置短超时 | 返回 504 和 `upstream_timeout`，记录实际耗时 |
| SRV-07 | 请求体超限 | POST 超过 1 MiB 的请求体 | 返回 413，服务随后仍能处理正常请求 |
| SRV-08 | 按 SID 落盘 | 使用两个不同 SID 提交 fairy/player 数据 | 返回 200；两组文件均存在且内容对应；索引元数据正确 |
| SRV-09 | 日志写入失败 | 使用只读或不可创建的日志目录 | 返回明确失败，不得返回 `ok:true`；服务不崩溃 |

## 7. 页面与战斗验收标准

除专门测试异常状态的用例外，每轮从已知初始状态开始。可用测试注入设置 HP、毒回合、题目和随机数，但必须在证据中说明注入值；不得把直接调用纯函数当作页面用例已通过。

| 用例 ID | 场景与步骤 | 通过条件 | 必备证据 |
|---|---|---|---|
| UI-01 | 打开地图并进入第一章 | 页面无脚本错误；第一章可进入；其余章节锁定状态符合存档 | 截图、浏览器错误记录 |
| UI-02 | 选择正确答案 | 只结算一次；出现攻击；MP/XP 按规则变化；存活时进入下一题 | 答题前后状态、题目与选项、截图 |
| UI-03 | 选择错误答案 | 只记录一次；攻击落空；当前无 LLM 分支按 v26 原规则进入下一题 | 错题记录、前后 HP/题目 |
| UI-04 | 连续点击及换怪空档输入 | 快速重复点击并在怪兽死亡后点击旧选项 | 不重复扣血、加经验或跳题；无异常 |
| UI-05 | 中毒最后一跳致死 | 注入 `HP<=毒伤害` 且剩余 1 回合，等待实际页面计时结算 | HP 为 0；显示死亡浮层；输入被锁定；不继续正常战斗 |
| UI-06 | 返回地图清理状态 | 分别在毒、冻结、续力状态可返回时回到地图，再等待超过原计时周期 | 原计时器不再扣血或施法；重新进入后无旧状态；记录无法主动返回时的替代操作 |
| UI-07 | 续力与大招计时 | 观察完整 4 秒续力并允许大招落地 | 续力条从 0 到 100；大招后无立即补普攻；计时归位符合规则 |
| UI-08 | 最终 Boss freeze 文案 | 触发冰霜魔王蓄力并检查精灵事件/请求 | 包含 `Absolute Freeze`，不得出现 `undefined` |
| UI-09 | 错题本入口 | 制造一条错题，回地图点击“错题本” | 弹窗实际可见；题目、正确项、错误项、次数正确；可关闭 |
| UI-10 | 精灵日志入口 | 产生一条日志，回地图点击“精灵日志” | 弹窗实际可见；事件、心情、文本、题目正确；可关闭 |
| UI-11 | 精灵事件问题快照 | 在旧题 LLM 请求未返回时切到新题，旧题答案与新题不同 | 旧事件日志仍对应旧题；旧答案按规则打码；不得以新题代替旧题打码 |
| UI-12 | 模型文本安全渲染 | 让测试模型返回带 HTML 标记的文本并打开气泡和日志 | 标记按文本显示，不创建元素、不执行脚本 |
| UI-13 | 无 LLM 基础可玩 | 关闭 LM Studio，完成答题、返回地图和错题本操作 | 不召唤精灵时核心流程无阻塞、无未捕获异常；不验收阶段 3 静态讲解 |

## 8. 题库数据验收标准

| 用例 ID | 检查项 | 通过条件 |
|---|---|---|
| DATA-01 | 总量与难度 | 198 题；d1/d2/d3 为 60/90/48；若有变更须先更新契约和说明 |
| DATA-02 | 题目 ID | 每题均有 ID；全库唯一；题库增删或重排不影响未修改题目的 ID |
| DATA-03 | knowledge | 每题至少一个合法标签；动词考点标签与题意一致 |
| DATA-04 | explanation | 所有动词题有非空讲解；抽查 go、buy、begin、wear 的答案与三形一致 |
| DATA-05 | 审计结果 | 结构、重复、答案、拼写等核心错误均为 0；刻意 WARN 有说明 |

## 9. `results.json` 数据格式

使用 UTF-8 编码的 JSON 数组。每个用例一条，不得省略失败或阻塞项。

```json
[
  {
    "id": "CMD-01",
    "title": "单元测试",
    "priority": "P0",
    "status": "PASS",
    "executedAt": "ISO 8601，含时区",
    "executor": "执行人",
    "preconditions": "干净工作区，依赖已就绪",
    "steps": ["npm test"],
    "expected": "退出码 0，fail=0，cancelled=0",
    "actual": "退出码 0；tests=25；pass=25；fail=0；cancelled=0",
    "metrics": {
      "exitCode": 0,
      "tests": 25,
      "pass": 25,
      "fail": 0
    },
    "evidence": ["commands/npm-test.log"],
    "defectId": "",
    "notes": ""
  }
]
```

字段约束：

- `id` 必须来自本标准；新增用例使用 `CUSTOM-001` 起编号并补充场景说明。
- `priority` 使用 `P0`、`P1`、`P2`。
- `status` 只能为 `PASS`、`FAIL`、`BLOCKED`、`N/A`。
- `actual` 必须写观测值，不得复制 `expected`。
- `metrics` 至少包含适用的数值结果；无数值时可为空对象。
- `evidence` 至少一项；`N/A` 可仅指向 `report.md` 中的范围说明。
- `FAIL` 必须填写 `defectId`，并在 `defects/` 提供同名记录。

## 10. 缺陷分级与最终通过门槛

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 核心流程不可用、数据严重错误、服务崩溃或死亡/结算错误 | 最后一跳致死不结算、服务器无法启动 |
| P1 | 声明的 v26 功能失败，或重要用户入口不可用 | 精灵审计崩溃、错题本/日志弹窗不可见、日志未落盘 |
| P2 | 有替代路径的体验、文档或非核心工具问题 | 文案旧口径、非阻塞展示问题 |

v26 最终通过必须同时满足：

1. 第 1.1 节范围内所有适用用例均为 `PASS`。
2. 无 `FAIL`、无未解除的 `BLOCKED`，P0/P1 未关闭缺陷为 0。
3. 所有命令退出码、HTTP 状态、页面实际观测和结果文件可相互对应。
4. `report.md` 汇总数量与 `results.json` 一致。
5. 阶段 3/4 未实现项只记为后续范围，不计入失败。

通过率仅作统计，不得用高通过率抵消 P0/P1 失败：

```text
通过率 = PASS 数 / (PASS 数 + FAIL 数 + BLOCKED 数) × 100%
```

## 12. 提交物最小清单

一次可评审的提交至少应包含：

- 完整的 `environment.json`、`results.json`、`report.md`。
- 7 类命令用例的原始结果；涉及 LLM 的用例附实际模型信息。
- 服务器正常、异常和日志落盘证据。
- 战斗、地图弹窗、快照和安全渲染的实际页面证据。
- 所有失败项的缺陷记录及修复后的新轮次结果。

只提交“25/25 通过”或若干成功截图，不满足本验收数据标准。
